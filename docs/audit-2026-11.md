# 홈커밍데이 2026 라이브 사이트 행사 전 점검 (2026-10-30)

대상: `index.html`(초대장), `live/index.html`(허브 · 질문 · 도우미 · 추첨 · 프로젝터 · 운영), `live/table/`, `people/`, `assets/ask.js`, `live/firestore.rules`
방법: Firebase 에뮬레이터(데모 프로젝트 `demo-hoco`) + Playwright로 행사 하루 전체를 시나리오 테스트. 프로덕션 DB에는 읽기 · 쓰기 모두 하지 않았다(외부 요청 전부 차단, 테스트 중 외부로 나간 Firebase 요청 0건 확인).

## 3. 문제 목록 (심각도 순)

표기: ✅ 이 PR에서 고침 · 🛠 운영진 조치 필요 · 💡 제안(큰 변경이라 이번엔 안 고침)

### Critical

**C1. 무료 한도 초과로 행사 중 실시간 기능이 멈출 위험** 🛠 (코드 쪽 일부 완화 ✅)
- 150명 기준 하루 읽기 추정 12만~19만 건, Spark 무료 한도는 5만 건(4장).
- 무료 한도는 태평양 시간 자정, 즉 **한국 시간 17:00에 초기화**된다. 행사(12:30~17:00)와 당일 오전 리허설이 모두 같은 하루 한도 안에 들어간다. 한도를 넘으면 그 시점부터 17:00까지 질문 · 추천 · 투표 · 추첨이 모두 실패한다.
- 조치: Blaze + 예산 알림(위 1번). 코드 쪽에서는 가장 큰 낭비였던 결과 공개 읽기를 줄였다(M2).

**C2. 프로젝터 화면에서 테이블 배치와 추첨 연출이 뜨지 않음** ✅
- 원인: `screen()`의 `seenSeq`가 선언되지 않아, 추첨 데이터를 받거나 화면 모드가 바뀔 때마다 `ReferenceError`가 났다. 그 뒤 코드(테이블 배치 그리기)가 실행되지 않고, 추첨 슬롯 연출도 프로젝터에서 한 번도 재생되지 않는다.
- 재현: `?screen`을 연 채로 운영 화면에서 ‘입장 · 체크인’ 시작 → 1라운드 테이블 칸이 비어 있음. 추첨 버튼 → 프로젝터에 슬롯이 안 뜸(휴대폰은 뜸).
- 수정: `let mode = null, seenSeq = null;` (테스트 `10-event-day` 2 · 6단계)

### High

**H1. 앞 투표 결과가 공개된 채로 다음 투표를 열면, 모든 휴대폰이 앞 결과 화면에 가려짐** ✅ (예전 ‘열기 = 결과 공개’ 버그의 변종)
- 재현: 투표 1 결과 공개 → 내리지 않고 투표 2 ‘열기’ → 참가자 화면에 투표 1 결과 전체 화면이 그대로 덮여 투표 2를 못 누름(각자 ‘닫기’를 눌러야 함).
- 수정: 투표를 열 때 다른 투표의 `open`과 `show`를 함께 끈다. 열기만 했을 때 결과 화면이 뜨지 않는 것도 회귀 테스트로 고정(`10-event-day` 4 · 4-1단계).

**H2. 리허설 후 ‘초기화’하고 운영 화면을 새로 열면, 열어 둔 프로젝터 · 휴대폰에 본 추첨 연출이 안 뜸** ✅
- 원인: 연출 번호 `seq`가 운영 화면 메모리에서 1부터 다시 시작한다. 이미 리허설 번호(예: 8)를 본 화면은 번호가 8을 넘을 때까지 새 추첨을 ‘이미 본 것’으로 보고 무시한다.
- 재현: `20-rehearsal-reset.spec.mjs`
- 수정: `seq`를 현재 시각 기준으로 항상 증가하게 바꿈(`Math.max(seq + 1, Date.now())`).

**H3. 로그인 없는 투표 · 추천이라 스크립트로 조작 가능** ✅ 일부 · 💡 나머지
`rules/firestore-rules.spec.mjs`에서 재현. `test.fail`로 표시된 항목은 아직 막히지 않은 것.

| 공격 | 이전 | 지금 |

- 남은 문제의 원인: 참가자를 구분하는 값(`pid`)이 공개 정보(기수+이름)로 누구나 계산할 수 있고, 서버는 요청한 사람이 누군지 모른다.
- 제안(💡): Firebase 익명 로그인 + App Check(reCAPTCHA Enterprise). 표 문서에 `uid`를 넣고 규칙에서 `request.auth.uid`로 1인 1표를 확인한다. 휴대폰 · 노트북 중복 방지(사람 기준)를 유지하려면 `pid → uid` 매핑 문서를 함께 만든다. 콘솔 설정과 흐름 변경이 필요해 행사 3주 전에 넣을지는 운영진 판단. 현실적인 위험은 “개발자 도구를 아는 참가자의 장난” 수준이므로, 당일에는 운영 화면 표 수와 참석자 수를 비교하는 것으로 대응할 수 있다.

**H4. 개인정보: 공개 저장소 · 공개 읽기로 ‘이름 비공개’ 안내와 실제가 다름** ✅ 대부분 · 💡 나머지

> **후속 조치(명단을 커밋하지 않는 방식으로 변경)**: 명단은 운영 화면 ‘명단’ 탭에서 CSV를 올려 Firestore에 저장한다(8장). 참가자는 기수+이름으로 계산한 칸 하나만 읽고(`roster/{key}` get), 전체 목록은 운영 계정만 읽는다. 참가자 카드는 카드 공개 동의자만 `state/people` 문서 하나에 담는다. `checkins`는 운영 계정만 읽는다. 프로젝터 테이블 배치(이름)는 운영 계정으로 로그인한 브라우저에서만 뜬다. 저장소의 `live/tables.json` · `people.json` · `tools/make_people.py`는 삭제했고, `.gitignore`가 CSV · 엑셀 · 명단 JSON을 막는다. 행사 후에는 ‘행사 데이터 전체 삭제’ 버튼 하나로 지운다. 남는 것: 이름을 알면 그 사람의 칸을 조회할 수 있다(설계상 필요). 추첨 연출용 응모자 이름(`draw/results`)은 행사 중 공개된다. `pid`를 아는 사람이 기수+이름을 추측해 맞춰 볼 수는 있다(명단이 공개되지 않아 훨씬 어려워짐).

아래는 변경 전 상태에 대한 원래 기록이다.

- 저장소가 public이다. `make_people.py --publish` 결과를 커밋하면 이름 · 기수 · 테이블 · 소개 · 링크가 GitHub와 git 기록에 영구히 남는다. README의 “30일 안에 삭제”는 파일 삭제만으로는 지켜지지 않는다(기록 재작성이 필요).
- 신원 시트는 “이름은 화면에 표시되지 않고 기수만 보여요”라고 안내한다. 하지만 `pid`는 기수+이름의 해시(소금값 없음)이고 투표 문서 id와 추천 목록에 그대로 저장되며 누구나 읽을 수 있다. 명단(`tables.json`)만 있으면 **누가 어느 선택지에 투표했는지, 어느 질문을 추천했는지** 역추적할 수 있다(테스트 ‘표 전체 목록과 각 표의 주인 읽기’).
- `checkins` 컬렉션(이름 · 기수 · 번호 · 체크인 시각)과 `draw/results.live.pool`(응모자 전원 이름)도 누구나 읽을 수 있다.
- 제안: (1) 명단 JSON은 비공개 저장소나 별도 호스팅에 두거나, 최소한 행사 뒤 기록을 지우는 절차를 정한다. (2) `checkins`는 `allow read: if isAdmin()`으로 바꾼다(참가자 화면에서 쓰지 않음, 프로젝터도 사용 안 함). (3) 신원 시트 문구를 “다른 참가자에게 이름이 보이지 않아요” 정도로 낮추거나, H3의 익명 로그인으로 바꿀 때 해시에 서버 비밀값을 넣는다.

### Medium

**M1. 띄어쓰기 없는 긴 글(주소 붙여넣기 등) 하나로 질문 화면 전체가 가로로 밀림** ✅
- 재현: 질문에 `https://...`처럼 60자 넘는 영문을 올림 → 375px 화면 문서 폭이 516px로 늘고, 곰돌이 버튼이 화면 밖으로 밀림.
- 수정: 질문 · 선택지 · 결과 · 당첨자 이름 · 챗봇 말풍선에 `overflow-wrap:anywhere`. 320 · 375px 전 화면 넘침 0(`40-mobile-a11y`).

**M2. 결과 공개 때 휴대폰마다 표 전체를 읽음(150명 기준 공개 1번에 약 2만 2천 읽기)** ✅
- 원인: 휴대폰 150대가 각각 `votes` 하위 컬렉션 전체(150건)를 구독했다. 150 × 150 = 22,500 읽기가 공개할 때마다 들고, 투표 3번이면 약 6만 8천 건이다. README와 주석에는 “결과 공개 때만 읽어 무료 한도 안”이라고 되어 있지만, 실제 부담은 그 공개 순간에 몰린다.
- 수정: ‘결과 공개’를 누를 때 운영 화면이 집계(`counts` · `total`)를 투표 문서에 함께 쓴다. 휴대폰은 그 문서만 읽고, ‘내 선택’은 이 기기에 남긴 값 또는 내 표 1건만 읽는다. 열린 채로 공개하면 운영 화면이 2초마다 집계를 맞춘다. 집계가 없는 예전 문서는 기존 방식으로 동작한다. 공개 1번당 22,650 → 약 300 읽기.

**M3. 인기 질문에 추천이 몰리면 일부가 실패(“다시 시도해 주세요”)** ✅ 완화
- 에뮬레이터에서 30명이 같은 질문에 동시에 추천하는 경우를 포함해 추천 150건 중 4~16건이 실패했다. 같은 문서에 동시에 쓸 때 생기는 경합이다.
- 수정: 실패하면 0.3~1초 뒤 한 번 자동 재시도.

**M4. 질문 도배 제한 없음** 💡
- 브라우저의 8초 게시 제한뿐이고, 서버 규칙에는 속도 제한이 없다. 당일에는 운영 화면의 ‘숨김’으로 대응할 수 있다. 근본 대응은 H3의 App Check.

**M5. 키보드 · 화면 읽기 접근성** ✅
- 신원 시트와 챗봇 창이 Esc로 닫히지 않았고, 챗봇 창을 열어도 포커스가 창 밖에 남았다. 기수 select, 이름 · 질문 입력칸, 운영 로그인 칸에는 이름(라벨)이 없었다(axe `select-name` · `label` critical).
- 수정: 두 창에 `role=dialog` · `aria-modal`, Esc로 닫기, 닫으면 원래 버튼으로 포커스 복귀, 챗봇은 열 때 입력칸(데스크톱)이나 닫기 버튼(휴대폰, 키보드가 바로 뜨지 않게)으로 포커스. 입력칸에 `aria-label`. ‘← Live’ · ‘다른 사람 찾기’ 링크 터치 높이 20 → 44px.

### Low

- **L1** 💡 `isAdmin()`이 이메일만 확인하고 `email_verified`는 확인하지 않는다. 운영 계정의 인증 메일을 먼저 확인한 다음 `&& request.auth.token.email_verified == true`를 추가하는 것을 권장. 지금 바로 넣으면 인증하지 않은 운영 계정이 막힐 수 있어 넣지 않았다.
- **L2** ✅ 운영 화면 추첨 탭에서 ‘다음 순서’ 버튼을 강조하는 클래스(`btn-ghost`)에 스타일이 없어 모든 버튼이 똑같아 보였다. 다음 순서를 `btn-primary`로 표시.
- **L3** 💡 초대장 푸터의 11px 보조 문구 대비가 3.93:1(기준 4.5:1). 사진 가로 스크롤 두 곳(`.then`, `.now`)은 키보드로 스크롤할 수 없다(`tabindex="0"` 권장). 초대장 디자인 영역이라 손대지 않음.
- **L4** 💡 Firebase 웹 API 키는 공개용이라 노출 자체는 문제가 아니다. 다만 GCP 콘솔에서 키를 HTTP 리퍼러(`homecoming.datamarket.ai.kr/*`, `tobigshoco.firebaseapp.com/*`)로 제한하면 다른 사이트에서 이 프로젝트를 쓰기 어려워진다.
- **L5** 참고: 같은 기수에 동명이인이 있으면 같은 `pid`가 돼 한 사람으로 센다(추천 · 투표 · 당첨 축하). 기수가 다르면 문제없음(테스트 명단에 기수만 다른 동명이인 18쌍 포함, 추첨 중복 없음 확인).
- **L6** 참고: 코드 주석 “참가자 휴대폰 70대”와 README의 “무료 플랜 읽기 한도 안에서 동작”은 150명 기준에는 맞지 않는다(요청대로 README는 수정하지 않음).

### 문제 없음으로 확인한 것

- **XSS**: 질문 · 명단 이름 · 참가자 소개 · 현장 등록 이름 · 챗봇 답변에 `<img onerror>`를 넣어도 허브 · 질문 · 프로젝터 · 운영 · 참가자 카드 · 챗봇 어디서도 실행되지 않고 글자 그대로 보인다(모든 출력이 `esc()`를 거침).
- **챗봇 링크**: 서버가 허용 목록 밖 키(`evil`, `javascript:...`)를 보내도 버튼이 만들어지지 않는다. 외부 링크는 `rel="noopener noreferrer"`.
- **운영 기능 권한**: 참가자 · 다른 이메일 계정은 진행 · 체크인 · 추첨 · 보너스 · 투표 열기 · 결과 공개 · 질문 숨김 · 답변 완료를 쓸 수 없다. 질문 생성 필드 · 길이 검증, 표 수정 · 삭제 금지, 서버 시각 강제도 정상.
- **git 기록의 비밀값**: 전체 50개 커밋에서 API 키(`sk-`, `sk-ant-`), 개인키, 서비스 계정, `.env`, 실명단 CSV 없음. 명단 JSON은 지금까지 빈 상태(`published:false`, 0명)로만 커밋됨. 공개된 것은 Firebase 웹 설정(공개용)과 운영 계정 이메일 주소.
- **챗봇 곰돌이 버튼**: 초대장 375px에서 하단 고정 바가 올라와도 겹치지 않고(버튼이 바 위로 이동), 고정 바 버튼도 가리지 않는다. 라이브 화면 맨 아래 요소도 가리지 않고, 결과 · 추첨 전체 화면이 뜨면 그 아래로 들어간다. 운영 · 프로젝터 · 도우미 전용 화면에는 뜨지 않는다. 버튼 크기 64px.

## 4. 부하 · 비용 (150명 동시 접속)

### 4-1. 리스너

참가자 휴대폰 1대(질문 화면 기준)의 실시간 구독: `state/program` 1, `questions` 1, `polls` 1(강제 전환용과 같은 쿼리라 SDK가 하나로 합침), `draw/results` 1. 결과 공개 중에는 예전 코드에서 `votes` 1개가 더 붙었다(이제 없음). 150명이면 동시 리스너 약 600~750개. Firestore 동시 연결 한도(100만)와는 거리가 멀어 문제없다. 프로젝터 · 운영 화면은 `votes`와 `checkins`까지 구독하지만 1~2대뿐이다.

### 4-2. 하루 읽기 추정 (과금 기준: 리스너가 받은 문서 1건 = 1읽기)

| 항목 | 계산 | 이전 코드 | 고친 뒤 |
| --- | --- | --- | --- |

- 에뮬레이터 실측(`tests/load/simulate.mjs`, 30명): 단계별 실측이 위 공식과 맞았다. 같은 문서가 짧은 시간에 여러 번 바뀌면 리스너가 묶어서 받으므로 실제 값은 상한보다 다소 적다. 150명 동시 실행은 에뮬레이터(프로세스 하나)가 일부 연결을 끊어 정확한 측정이 안 됐다. 실제 서비스 성능 측정이 아니다.
- 결론: 고친 뒤에도 무료 한도의 2배 이상이다. 화면 열기와 추천 반영은 실시간 구조에서 기본으로 드는 비용이라 크게 줄이기 어렵다. **Blaze 전환이 필요**하다. 비용은 Firestore 읽기 10만 건당 약 0.03~0.06달러(리전별)라 12만~19만 건이어도 1달러 미만이다(무료분 5만 건은 Blaze에서도 차감).
- 더 줄이려면(💡): `initializeFirestore(..., { localCache: persistentLocalCache() })`로 오프라인 캐시를 켜면 30분 안에 다시 연 화면은 바뀐 문서만 읽는다. 다만 캐시로 인한 첫 화면 오래된 값(예: 지난 추첨 연출이 다시 재생)을 처리하는 코드가 필요해 이번에는 넣지 않았다.

## 5. 모바일 · 접근성

- **가로 넘침**: 320 · 375px에서 초대장 · 허브 · 질문 · 추첨 · 도우미 · 내 테이블 · 참가자 카드 · 운영 로그인, 그리고 신원 시트 · 결과 전체 화면 · 추첨 슬롯까지 넘침 0(M1 수정 후).

- **터치 영역**: 24px 미만(WCAG 2.5.8 AA)이던 독립 버튼 · 링크(‘← Live’, ‘다른 사람 찾기’)를 44px로 키웠다. 남은 것은 초대장 문장 안의 인라인 링크로, 기준상 예외다. 44px 미만이지만 24px 이상인 요소(정렬 · 필터 칩, 연사 대상 버튼 등 높이 26~36px)는 그대로 두었다.
- **대비(axe)**: 라이브 화면들은 위반 없음. 초대장 푸터 1곳(L3).
- **키보드**: 질문 화면은 Tab만으로 질문 입력 → 게시까지 갈 수 있다. 신원 시트는 열리면 기수 칸에 포커스, Esc로 닫히고 원래 버튼으로 돌아간다. 챗봇도 같다(M5 수정 후).

## 8. 명단 운영 방법 (명단을 커밋하지 않는 방식)

1. RSVP 시트를 `tools/people.template.csv` 열 이름(no, name, gen, t1, t2, intro, topic1, topic2, card, linkedin, remember, instagram, other, photo)으로 정리한다. 구글 시트는 ‘다운로드 › CSV’, 엑셀은 ‘다른 이름으로 저장 › CSV’로 저장한다. EUC-KR(엑셀 기본) · UTF-8 모두 된다. **이 파일은 저장소 폴더에 두지 말 것**(둬도 `.gitignore`가 막는다).
2. `live/?admin` 로그인 › **명단** 탭 › 파일 고르기. 인원 · 카드 공개 수 · 사진 제공 수 · 테이블 수와 오류(번호 중복 · 빈 번호/이름), 경고(기수 형식 · 빈 테이블 · 같은 기수 동명이인)를 확인하고 ‘이 명단으로 올리기’를 누른다. 다시 올리면 전체가 새 명단으로 바뀐다.
3. 명찰 QR: `python3 tools/make_qr.py 명단.csv` → `qr/badge/`(커밋 안 됨).
4. 프로젝터는 운영 노트북에서 로그인한 브라우저의 ‘프로젝터 화면’ 링크로 연다. 로그인하지 않은 브라우저에서는 테이블 배치에 이름 대신 “명찰에 적힌 테이블 번호로 앉아 주세요”가 뜬다.
5. 행사 후: 명단 탭 › ‘명단 내리기’(명단 · 카드만 지움) 또는 ‘행사 데이터 전체 삭제’(`삭제` 입력, 명단 · 카드 · 질문 · 투표 · 체크인 · 추첨 결과 · 보너스 모두 지움).
6. 읽기 비용: 참가자 명단 조회 1건, 내 테이블 2~3건, 참가자 카드 화면 2건(카드 전체가 문서 하나), 운영 화면 열기와 프로젝터 테이블 화면 전환은 각각 약 150건. 4장 추정치에 큰 영향 없음.
